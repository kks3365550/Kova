# Track 2-3: 청킹 아키텍처 비교 분석 및 프로토타입 설계서
(Fixed Block vs FastCDC vs Pack Container vs Hybrid)

> **[원칙 및 제약 사항 준수]**
> - 본 문서는 순수 아키텍처 설계 및 모델링 문서이며, 기존 `BackupSystem` 프로덕션 코드에 대한 어떠한 수정이나 구현 코드도 포함하지 않습니다.
> - Track 2-1 및 Track 2-2에서 확보한 **Whole-file CAS 실측치**를 절대 기준선(Ground Truth Baseline)으로 유지합니다.
> - 실측되지 않은 모든 항목은 **[예상/이론 모델(Estimated / Theoretical Model)]**로 엄격히 구분하여 기술합니다.

## 1. 개요 및 설계 배경

Track 2-1과 Track 2-2의 10GB 단일 파일 실측을 통해, 현행 **Whole-file CAS (Whole-file Content-Addressable Storage)**는 다음과 같은 물리적 한계를 입증했습니다:
1. **읽기 I/O 증폭 (I/O Read Amplification)**: 단 1MB(0.0098%)만 변경되어도 10GB 전체 파일(10,739,804,028 B)을 전수 재독출 (증폭비 10,240배).
2. **시간 단축 효과 부재**: 최초 10GB 백업(15.92초) 대비 1MB 변경 증분 백업(15.62초) 간 수행 시간 차이가 0.3초 미만.
3. **저장소 중복 소비**: 파일 전체 단위 해시 변경으로 인해 10GB 분량의 신규 블롭이 통째로 복제 생성.

본 설계서는 이러한 한계를 극복하기 위해 검토 가능한 4대 청킹 패러다임(**Fixed Block**, **FastCDC**, **Pack Container**, **Hybrid**)을 현행 Whole-file CAS와 다각도로 비교 분석하고, 향후 프로토타입 단계에서 검증할 최소 실험 매트릭스를 정의합니다.

## 2. 4대 청킹 아키텍처 개요 및 특징

```
[1. Fixed Block]      : 고정 크기(예: 1MB/4MB)로 균등 분할
                        ┌───────┬───────┬───────┬───────┐
                        │ Block │ Block │ Block │ Block │ (오프셋 덮어쓰기에 강함, 바이트 삽입/삭제 시 경계 밀림)
                        └───────┴───────┴───────┴───────┘

[2. FastCDC]          : Gear 해싱 기반 내용 정의 가변 청킹 (평균 1MB~4MB)
                        ┌─────┬───────┬───┬─────────┬──┐
                        │Chunk│ Chunk │Chk│  Chunk  │Ch│ (바이트 삽입/삭제 시에도 경계 국소화)
                        └─────┴───────┴───┴─────────┴──┘

[3. Pack Container]   : 수천~수만 개의 청크 블롭을 단일 컨테이너 파일에 패킹
                        ┌───────────────────────────────┬─────────┐
                        │ Chunk 1 | Chunk 2 | Chunk 3...│ Index/DB│ (NTFS inode/소형 파일 폭증 원천 차단)
                        └───────────────────────────────┴─────────┘

[4. Hybrid]           : 파일 크기 임계치(예: 64MB~100MB) 기반 분기
                        ├─ 소형 파일 (< 64MB) ───► 현행 Whole-file CAS (오버헤드 0, 복원 속도 극대화)
                        └─ 대형 파일 (>= 64MB) ──► FastCDC + Pack Container (I/O 및 저장소 절감)
```

## 4. 아키텍처별 세부 평가 및 트레이드오프

### 4.1 Fixed Block (고정 크기 청킹)
- **장점**:
  - 구현이 극도로 단순함 (`f.read(4 * 1024 * 1024)` 루프).
  - 고정 오프셋 데이터 덮어쓰기(DB 파일, VHDX, 로그 덮어쓰기 등)에 대해 10GB 전체 독출 없이 해당 블록만 읽어 처리 가능.
- **치명적 단점 (Boundary Shift Issue)**:
  - 파일 중간에 단 1바이트라도 삽입(Insert)되거나 삭제(Delete)되면, 그 지점 이후의 모든 고정 경계가 1바이트씩 밀려 **이후의 모든 블록 해시가 100% 무효화(중복 제거 0%)**됨.
  - 별도 Pack 구조 없이 개별 파일로 저장할 경우 10GB 파일 1개당 2,500개의 `.blob` 파일이 생성되어 Windows NTFS 성능을 저하시킴.

### 4.2 FastCDC (Content-Defined Chunking)
- **장점**:
  - **내용 기반 경계 분할(Gear Hash)**을 통해 바이트가 삽입/삭제되어도 변경 지점 주변 1~2개 청크를 지나면 다시 경계가 동기화됨.
  - 삽입/삭제 패턴에서도 99% 이상의 높은 중복 제거율(Deduplication Ratio) 유지 가능.
- **트레이드오프**:
  - 순수 파이썬 구현 시 슬라이딩 윈도우 바이트 연산 속도가 느려질 수 있으므로, C-Extension 또는 최적화된 바이트 연산이 필수적임.
  - 가변 길이 청크이므로 메타데이터에 각 청크의 `offset`과 `length`를 함께 관리해야 함.

### 4.3 Pack Container (패킹 컨테이너)
- **도입 필요성**:
  - Fixed Block이든 FastCDC이든, 10GB 파일 1개에서 수천 개의 블롭 파일(`00/sha.blob`, `01/sha.blob`...)이 디스크에 직접 생성되면 Windows NTFS 디렉토리 엔트리 경합과 MFT 파편화가 발생함.
  - 백업 저장소에 수만 개의 작은 파일 대신, 수백 MB 단위의 **Pack Container 파일(예: `pack_001.bin`)** 내부에 청크들을 연속 기록하고 오프셋 인덱스를 관리하는 것이 엔터프라이즈(Git, Restic, Borg) 표준임.
- **트레이드오프**:
  - 스냅샷 삭제(Retention) 시 미사용 청크를 회수하는 Garbage Collection(Compaction/Pack 재패킹) 로직이 추가되어야 함.

### 4.4 Hybrid (실용적 절충안)
- **전략**:
  - **소형 파일 (< 64MB)**: 현행 Whole-file CAS 유지. 분할 오버헤드, 인덱스 부하를 없애고 단일 원자적 블롭으로 최고 속도 백업/복원.
  - **대형 파일 (>= 64MB)**: FastCDC + Pack Container 파이프라인으로 전환하여 I/O 증폭과 스토리지 낭비를 원천 차단.
- **평가**:
  - 대부분의 일상 파일(소스코드, 문서, 소형 이미지)은 기존 안정된 File CAS로 빠르게 통과시키고, VM 디스크/대용량 DB/비디오 등 대형 파일에만 청킹을 집중 적용하므로 시스템 효율성이 가장 높음.

## 5. Track 2-4 프로토타입 검증을 위한 최소 실험 매트릭스 제안

프로덕션 코드에 영향을 주지 않고 격리된 벤치마크 환경에서 성능과 효율을 실증하기 위해, 다음의 **3×3×2 최소 실험 매트릭스**를 제안합니다.

### 5.1 검증 대상 구조 (3가지 엔진)
1. **Engine A (Baseline)**: 현행 Whole-file CAS
2. **Engine B (Fixed Block Prototype)**: 4MB 고정 블록 엔진
3. **Engine C (FastCDC Prototype)**: 평균 4MB 가변 청크 엔진 (Min 1MB, Max 8MB)

### 5.2 변이 패턴 테스트 조건 (3가지 변이)
- **Pattern 1: In-Place Mutation (덮어쓰기)** - 10GB 파일 중앙의 10MB 덮어쓰기
- **Pattern 2: Byte Insertion (바이트 삽입/경계 이동)** - 10GB 파일 중앙에 1KB 데이터 삽입 (전체 경계 Shift 유발)
- **Pattern 3: Multi-spot Mutation (분산 변경)** - Head, Middle, Tail 3개 지점에 각각 1MB씩 덮어쓰기

### 5.3 측정 지표 (Metrics)
1. **I/O Read 바이트**: 변경 감지 및 재처리 시 읽은 총량 (10GB 대비 절감율 %)
2. **Chunk 재사용률 (Dedup %)**: 기존 청크 중 재사용된 비율
3. **Wall Clock Time (수행 시간)**: 청킹 및 해싱 소요 시간 (초)
4. **저장소 순증가량 (New Stored Bytes)**: 디스크에 새로 기록된 바이트 수
5. **복원 속도 (Restore Throughput)**: 10GB 원본으로 재조립하는 데 걸리는 시간 및 MB/s

## 6. 결론 및 다음 단계 제언
- 본 설계를 통해 현행 Whole-file CAS의 대형 파일 취약점(10GB 전수 재독출)을 극복하기 위한 기술적 대안들의 득실이 명확히 정립되었습니다.
- 사용자의 후속 지시가 있을 때까지 **기존 프로덕션 코드(`core/*`)는 일체 변경하지 않으며**, 향후 별도의 독립 프로토타입 스크립트를 통해 위 실험 매트릭스(Engine A vs B vs C)를 순수 계측할 준비를 유지합니다.
