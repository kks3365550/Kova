
## 왜 이력 정리를 아직 하지 않았는가

`git filter-repo` 는 되돌릴 수 없고 다음 비용이 따른다.

1. **154개 커밋 SHA가 전부 바뀐다**
2. 태그 13개 재생성 필요
3. 원격 force-push — 이 창에서 알아차리기 어렵다
4. 이미 24시간 이상 공개 상태였으므로 **크롤링되었을 가능성**

**핵심은 4번이다.** 이력에서 지워도 이미 읽혔을 수 있다.
그러므로 순서는 반드시:

```
키 회전 (값 자체를 무효화)  →  그 다음  →  이력 정리 (기록 삭제)
```

이력 정리를 먼저 하면 "지웠다"는 안심만 생기고 실제 위험은 그대로다.

그리고 배포 키 회전에는 기술적 장애물이 있다.

```
core/updater.py 는 PUBLIC_KEY_PATH 단일 경로만 검증한다.
D:\백업시스템_설치용\keys\release_ed25519.pub 에 구 공개키가 박혀 있다.
→ 공개키를 교체하면 이미 배포된 모든 PC 가 새 업데이트를 거부한다.
```

따라서 키 회전은 다중 공개키(keyring) 지원이 선행되어야 한다.
새 키로 v2.13.8 을 배포해 클라이언트가 새 키를 배운 뒤,
구 공개키를 제거하는 2단계가 필요하다. 이 작업은 사용자가 결정해야 한다.

`tools/scan_secrets.py` + CI `secret-scan` 잡.

탐지 규칙:

| 규칙 | 심각도 |
|---|---|
| PEM 개인키 헤더 | CRITICAL |
| Firebase API 키 (`AIza…`) | CRITICAL |
| GitHub 토큰 (`ghp_…` 등) | CRITICAL |
| AWS access key (`AKIA…`) | CRITICAL |
| Slack 토큰 (`xox…`) | CRITICAL |
| 하드코딩된 password | HIGH |
| 하드코딩된 api_key / secret / token | HIGH |

검증 결과:

```
현재 HEAD (392개 파일)          : 0건  (깔끔)
이력 전체 (154커밋)              : 31건 (미처리, 문서 참조)
실제 유출 파일 3종              : 모두 탐지됨
테스트 픽스처 암호 (오탐)       : 경로 예외로 제외
```

### 설계 판단 두 가지

**1. CI 는 추적 파일만 검사한다**

이력 전체를 CI 게이트에 넣으면 기존 유출 31건 때문에 CI 가 영구히 실패한다.
빨간 CI 는 아무도 보지 않게 되므로 방치된다.
이미 알고 있는 문제는 이미 알고 있고, CI 는 앞으로 오는 실수만 막는다.

전체 이력 감사는 수동으로 실행한다:

```powershell
python tools/scan_secrets.py --history     # 79초
```

**2. 비밀은 커밋하면 반드시 추적 파일이 된다**

추적 파일 검사만으로 새 유출은 전부 막힌다. 이력 전체 검사가 필요한 유일한
 경우는 "커밋 후 추적을 해제"한 경우인데, 이것까지는 CI 가 잡지 못한다.
 그래도 그 빈도는 낮고, 추가 비용이 지속적 CI 정지를 초당하는 것보다 낫다.
