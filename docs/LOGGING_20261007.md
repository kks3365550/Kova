# 백업 로깅 실측 보고 (2026-10-07)

## 🔴 발견: 스케줄러 백업 로그가 존재하지 않았다

### 증명

스케줄러 등록 명령 (实测 확인):

```
Execute : "...\.venv\Scripts\pythonw.exe"
Argument: "...\cli_backup.py" --profile "prof_custom_selected"
```

`pythonw.exe` 는 콘솔이 없는 Python 실행기다. 표준출력이 연결되어 있지
않으므로 `print()` 출력은 어디에도 남지 않는다.

직접 실측한 결과:

```
pythonw.exe 로 print("X") 실행  -> 파일 기록 0건
pythonw.exe 로 FileHandler 로그 -> 파일에 정상 기록됨
```

### 실제 피해

```
2026-10-07 09:00:01  스케줄러 실행
LastTaskResult      = 0        ("정상 종료")
저장소 스냅샷       = snap_20261007_090323_235248.json  (생성됨)
로그 파일            = (없음)
```

백업은 실제로 성공했다. 그런데 **왜, 무엇을, 얼마나 했는지 기록된 곳이
어디에도 없었다.** 내일 같은 상황이 반복되면 구분할 방법이 없다.

`LastTaskResult = 0` 은 "프로세스가 예외 없이 끝났다"는 뜻일 뿐이다.
백업이 NAS에 복제됐는지, 몇 개를 정리했는지, 어떤 경로를 건너뛰었는지는
어디에도 없다.

## 해결

### core/logging_setup.py (신규)

`logs/backup.log` 로 쓰는 로거를 구성한다.

| 결정 | 이유 |
|---|---|
| 파일 로깅 우선 | 표준출력과 무관하게 기록됨 |
| 5MB 회전, 이전 1개 | 백업 디스크 보호 |
| `propagate = False` | 다른 라이브러리의 루트 설정에 레벨이 끌려가지 않음 |
| `_CONFIGURED` 가드 | 같은 프로세스 재구성 시 핸들러 중복 방지 |
| 예외는 `exc_info=True` | 실패 원인은 대부분 예외 안쪽에 있음 |

로그 디스크를 만들 수 없는 경우에도 백업 자체는 계속되도록
`basicConfig` 로 폴백한다.

### cli_backup.py

`print()` 65줄을 `_say` / `_warn` / `_error` 로 교체했다.
세 함수는 **파일 로그 + 표준출력에 동시에** 남긴다.
`pythonw.exe` 환경에서는 파일 로그가, 콘솔 실행에서는 표준출력이 쓰인다.

추가로 결함 3건을 함께 고쳤다:

| 위치 | 문제 | 수정 |
|---|---|---|
| `_run_offsite_replication` | 오프사이트 상태 저장 실패가 `pass` 로 무음 | `log.error(..., exc_info=True)` |
| `except Exception as e` (백업 실패) | 실패 원인이 스택 없이 한 줄로만 남음 | `exc_info=True` 로 스택 트레이스 기록 |
| `except Exception as e` (백업 실패) | 실패 상태 저장 자체가 실패하면 기록 없음 | 별도 로그 + 저장 시도 |

### core/retention.py

스냅샷 목록 읽기 실패 시 상태명이 `no_snapshots` 였습니다.

```python
except Exception:
    return {... "status": "no_snapshots"}
```

`no_snapshots` 는 "스냅샷이 없다"는 뜻인데, 실제로는 "목록을 못 읽었다"입니다.
저장소가 손상돼도 두 경우를 구분할 수 없어 **디스크가 계속 차는데 아무도
모르는** 상태가 됩니다.

수정 후:

```python
except Exception as e:
    log.warning("스냅샷 목록 읽기 실패, 보존 정책 적용 중단...", exc_info=True)
    return {... "status": "list_failed", "error": str(e)[:300]}
```

`list_failed` 를 쓰는 코드가 어디에도 없음을 확인했다(전수 검색).
실측 검증:

```
빈 저장소         -> safe_minimum  (기존과 동일)
목록 읽기 실패    -> list_failed
원인 메시지       -> '의도적 실패: 저장소 손상'  (이제 남는다)
```

### 회귀 테스트 (tests/test_backup_logging.py, 9건)

- 로그 파일이 logs/ 아래 절대 경로인가
- 회전 핸들러가 설치돼 있는가
- 회전 임계값이 상한을 넘지 않는가
- 핸들러가 중복 추가되지 않는가
- propagate 가 꺼져 있는가
- 실제로 파일에 기록되는가
- cli_backup.py 가 파일 로거를 쓰는가
- 예외가 스택 트레이스와 함께 남는가

## 남은 무음 예외: 167건 (전부 손대지 않음)

AST로 전수 조사한 결과 `core/` 33개 모듈에 예외를 삼키는 지점 167건이 있다.

| 모듈 | 건수 |
|---|---:|
| storage.py | 23 |
| metadata_db.py | 20 |
| snapshot.py | 17 |
| lock.py | 10 |
| app_scanner.py | 9 |
| driver_backup.py | 8 |
| registry_backup.py | 7 |
| restore.py | 7 |
| scheduler.py | 7 |
| system_image.py | 7 |

**의도적으로 손대지 않았다.** 이유:

1. 다수가 정상 제어 흐름이다. 임시파일 정리, 존재하지 않는 파일 무시,
   Windows 전용 API 부재 처리 등이 섞여 있다.
2. 남은 대부분은 `Web UI 경로` 다. 서버는 수동 기동이라 실패가 화면에
   즉시 보인다. 스케줄러 경로가 아니라면 지금 당장 위험하지 않다.
3. 무작정 로깅을 추가하면 로그가 폭발해 진짜 원인을 묻는다.
   백업 시스템에서 로그 폭발은 로그 부재와 같이 나쁘다.

**판단 기준을 다음 문서에 남겼다**: 백업 결과(성공/실패/무결성)에 영향을
주는 예외만 로깅한다. UI 전용 예외는 서버 콘솔에 이미 보인다.

우선순위는 이 순서다:

1. `snapshot.py` 259행, 464행, 657행 — 매니페스트/스냅샷 상태 기록
2. `storage.py` 245행, 594행, 766행 — 블롭 쓰기/읽기 해시 무결성
3. `restore.py` 296행 — 손상 블롭 (현재 메시지만 반환, 로그 없음)
4. `replication.py` 306행 — 워커 future.result() 예외

각 항목은 회귀 테스트와 함께 반영해야 한다.
