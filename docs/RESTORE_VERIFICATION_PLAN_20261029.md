# Kova 복원 검증 보강 계획 (Claude Code 작업 지시서)

- 작성일: 2026-10-29
- 기준 버전: v2.17.21 (main, shallow clone 기준 정적 분석)
- 목적: "백업 성공"이 아니라 "복원 가능"을 주기적으로 증명하고, 검증 실패가 반드시 사용자에게 도달하게 한다.

---

## 0. 작업 방식 (Claude Code에게)

1. **코딩 전에 1장의 "현황 검증" 결과부터 보고한다.** 아래 발견사항은 정적 읽기 기반이라 틀릴 수 있다. 각 항목을 코드와 테스트로 확인하고 `확인됨 / 반박됨 / 부분적` 으로 표시한 뒤 진행한다.
2. Phase 순서대로 진행하고, Phase마다 별도 커밋으로 나눈다.
3. **백업 저장소 포맷(blobs, snapshots, pack)과 Rust 매니페스트 스키마는 변경하지 않는다.** 변경이 불가피하면 멈추고 사용자에게 설계안을 먼저 제시한다 (하위호환이 걸린 변경).
4. 모든 수정은 실패를 재현하는 테스트를 먼저 작성하고(red), 수정 후 통과(green)시킨다.
5. 기존 테스트 전체 통과 유지: `pytest` 및 `engine_rust` 의 `cargo test`.
6. 미니PC 09:00 자동 백업 흐름(`core/scheduler.py` `_run_profile_backup`)의 성공/실패 판정 의미를 바꾸지 않는다.

## 1. 현황 (정적 분석 결과, 검증 필요)

이미 3계층 검증이 있다. 구조는 좋지만 **실패해도 조용히 지나가는 경로**가 여럿 있다.

| 계층 | 위치 | 하는 일 | 주기 |
|---|---|---|---|
| Tier 1 | `core/scheduler.py` `_verify_rust_snapshot`, `core/snapshot.py:758` | 백업 직후 계층화 표본 20개 실제 복원 대조 | 매 백업 |
| Tier 2 | `core/scheduler.py` `_run_tier2_weekly_audit` | 전 스냅샷 매니페스트 Ed25519 서명·지문 검사 | 주 1회 |
| Tier 3 | `core/scheduler.py` `_run_tier3_monthly_audit` → `disaster_recovery.audit_repository` | 전 블롭 SHA-256 Bit-Rot 전수 검사 | 월 1회, 02~05시 |

### 발견사항 (심각도순)

**F1 [P0] Tier 2·3 실패가 알림으로 가지 않는다.**
- `_run_tier2_weekly_audit`, `_run_tier3_monthly_audit` 는 손상을 감지해도 `self._log(..., level="ERROR")` 만 한다.
- 알림(`_notify_failure` → `windows_toast.notify_backup_failed`)은 백업 실패 경로에서만 호출된다.
- Tier 1 의 `skipped`, "검증을 수행하지 못했습니다" 경로도 WARNING 로그만 남긴다.
- 결과: 월간 감사가 손상 블롭을 찾아도 사용자가 로그를 열어보기 전에는 모른다.

**F2 [P0] 기본 엔진(Rust) 스냅샷은 Tier 2 주간 검사가 사실상 아무것도 검사하지 않는다.**
- 기본값 `backup_engine: "rust"` (`core/config.py:52`).
- Rust 매니페스트는 `files` 필드를 쓰고 `entries: None` (`engine_rust/src/main.rs:431-432`). `manifest_signature`, `ed25519_signature` 를 기록하지 않는다 (`engine_rust/src` 에 해당 필드 없음).
- Tier 2 는 `"ed25519_signature" in m` 이 거짓이면 서명 검사를 건너뛰고, `expected_sig and entries` 가 거짓이면 지문 검사도 건너뛴다.
- 그 상태로 `"N개 스냅샷 ... 무결성 100% 정상"` 을 로그에 남긴다. **검사하지 않은 것을 통과로 보고한다.**

**F3 [P0] Tier 3 는 암호화 블롭을 검증하지 않는다.**
- `disaster_recovery.audit_repository` 의 `check_blob`: 헤더가 `ENC\x01` 이면 크기 32바이트 이상인지만 보고 `True` 를 반환한다.
- 저장소 암호화(`core/crypto_at_rest.py`)를 켜면 월간 Bit-Rot 감사가 전 블롭을 "정상"으로 보고한다.
- 반면 `core/verify.py` `IntegrityVerifier` 는 `crypto_engine` 을 받는다. Tier 3 가 이쪽을 쓰지 않는 이유를 확인할 것.

**F4 [P1] 감사 상태가 "실행 전"에 기록된다.**
- `_check_deep_scans` 는 스레드 시작 전에 `last_weekly` / `last_monthly` 를 `now` 로 저장한다.
- 감사가 예외로 죽거나 프로세스가 재시작되면 다음 주기(7일/30일)까지 재시도하지 않는다.
- Tier 3 는 02~05시 창에서만 돌므로, 미니PC가 그 시간에 꺼져 있으면 계속 밀린다. 실제로 마지막 성공 시각을 확인할 방법이 로그뿐이다.

**F5 [P1] 전체 복원 리허설이 없다.**
- Tier 1 은 표본 20개, Tier 3 는 블롭 단위 해시다. "특정 스냅샷 전체를 처음부터 끝까지 복원해서 원본과 대조"는 정기 실행되지 않는다.
- 증분 체인·pack 통합(`pack_consolidator.py`) 이후의 복원 경로 결함은 표본으로는 놓칠 수 있다.

**F6 [P1] 구버전 저장소 복원 호환성 회귀 테스트가 없다.**
- 엔진 업데이트 후 과거 버전이 만든 저장소를 새 엔진이 복원하는지 CI 에서 확인하지 않는다 (확인 필요: `tests/` 에 고정 fixture 저장소 존재 여부).

**F7 [P2] 검증 상태가 대시보드에 보이지 않는다.**
- 계층별 마지막 성공 시각과 결과를 한눈에 볼 수 없다.

## 2. 작업 계획

### Phase 1 — 실패가 반드시 도달하게 (F1, F4) [P0]

1. `core/notify.py` (가칭) 단일 알림 진입점 추가.
   - `notify(event: str, severity: "critical"|"warning"|"info", title, detail)`
   - **외부 채널(텔레그램, 이메일, 웹훅 등)은 사용하지 않는다 (사용자 결정, 2026-10-29).** 네트워크 송신 코드를 추가하지 않는다.
   - 채널은 로컬 3중으로 구성한다. 토스트는 한 번 뜨고 사라지므로 단독으로는 침묵 실패를 막지 못한다. 그래서 **사용자가 확인할 때까지 사라지지 않는 상태**를 핵심으로 둔다.
     1. **영속 경보 기록**: `critical`/`warning` 경보를 상태 파일(원자적 쓰기)에 `미확인`으로 저장. 사용자가 대시보드에서 확인 처리하기 전까지 유지. 같은 원인의 반복 경보는 1건으로 묶고 발생 횟수만 증가.
     2. **트레이 아이콘 상태**: `tray_app.py` 가 미확인 `critical` 이 있으면 경고 아이콘과 툴팁을 유지. 기존 `_monitor_server_status` 폴링에 미확인 경보 조회를 추가.
     3. **대시보드 배너 + 토스트**: 대시보드 상단 고정 배너. 토스트는 최초 발생 시와, 미확인 상태로 24시간이 지날 때마다 재발송.
   - 알림 처리 실패가 백업·감사 결과를 바꾸면 안 된다.
2. 호출 지점 연결:
   - Tier 1: `passed` 가 아닌 모든 결과(`failed`, `skipped`, 검증 미수행 예외) → `warning` 이상.
   - Tier 2: 손상 스냅샷 ≥1 → `critical`. 검사 불가 스냅샷 존재 → `warning` (F2 연계).
   - Tier 3: 손상 블롭 ≥1 → `critical`. 감사 예외 → `critical`.
   - 기존 백업 실패 경로는 새 진입점으로 이전하되 동작 유지.
3. 감사 상태 분리 (F4):
   - `last_attempt`, `last_success`, `last_result` 를 계층별로 기록. 주기 판정은 `last_success` 기준.
   - 실패·중단 시 다음 루프(또는 다음 야간 창)에서 재시도. 연속 실패 횟수 기록.
4. **데드맨 스위치**: 계층별 허용 공백 초과 시 경보.
   - Tier 1: 마지막 검증 성공이 36시간 초과 (매일 09:00 백업 기준).
   - Tier 2: 9일 초과. Tier 3: 35일 초과.
   - 스케줄러 루프 안에서 판정하되, **스케줄러 자체가 죽은 경우**를 위해 Windows 작업 스케줄러에 별도 경량 점검 작업(하루 1회, 상태 파일만 읽고 알림)을 등록하는 안을 검토하고 설계만 제시한다(구현은 사용자 승인 후).

테스트:
- 각 계층의 실패를 주입(블롭 변조, 매니페스트 변조, 예외 주입)하면 `notify` 가 올바른 severity 로 1회 호출되는지.
- 알림 처리(상태 파일 쓰기, 토스트) 실패 시 백업 결과가 바뀌지 않는지.
- 미확인 경보가 재시작 후에도 유지되고, 확인 처리 후에만 사라지는지.
- 동일 원인 경보가 중복 생성되지 않고 횟수만 증가하는지.
- 감사 중 예외 후 다음 루프에서 재시도되는지.
- 데드맨 임계 초과 시 경보, 미만 시 무경보.

### Phase 2 — Rust 스냅샷을 실제로 검사 (F2) [P0]

포맷 변경 없이 먼저 할 수 있는 것:
1. Tier 2 에서 Rust 매니페스트(`files` 형식)를 인식한다. `_verify_rust_snapshot` 의 `files → entries` 변환 로직을 공용 함수로 추출해 재사용.
2. 서명·지문이 없는 Rust 스냅샷에 대해 최소한 **참조 청크 존재 검사**(missing blob)와 JSON 구조 검사를 수행.
3. 로그와 알림에서 "검증됨 N / 서명 없음(구조·존재만 검사) M / 손상 K" 로 구분 보고. **검사하지 않은 것을 '정상'으로 세지 않는다.**

포맷 변경이 필요한 것 (설계안만 제시, 구현 보류):
4. Rust 스냅샷에도 `manifest_signature` 와 Ed25519 서명을 부여하는 방안. 선택지: (a) Rust 엔진이 직접 기록, (b) Python 스케줄러가 Rust 완료 후 별도 서명 파일(`snapshots/<id>.sig`)을 원자적으로 기록. 하위호환·원자성·키 접근 측면 비교표를 작성해 사용자에게 제시.

테스트:
- Rust 형식 매니페스트에서 청크 하나 삭제 → Tier 2 가 손상으로 보고.
- Rust 형식 매니페스트만 있는 저장소에서 "100% 정상" 문구가 나오지 않는지.

### Phase 3 — 암호화 저장소 Bit-Rot 감사 (F3) [P0]

1. Tier 3 를 `IntegrityVerifier.audit_entire_repository` (crypto_engine 주입)로 일원화할 수 있는지 확인. 두 함수의 커버리지 차이(누락 블롭, 고아 블롭, pack 저장소, 암호화 블롭)를 표로 정리 후 결정.
2. 암호화 블롭은 복호화 → 압축 해제 → SHA-256 대조까지 수행. 키가 없으면 "검증 불가"로 분류하고 `warning` 알림 (정상으로 세지 않음).
3. pack 형식(`core/pack_format.py`, Track2) 저장소도 감사 대상에 포함되는지 확인하고 누락 시 포함.
4. 전수 검사 부하: 미니PC 성능 기준으로 처리량을 측정하고, 필요하면 I/O 제한(throttle) 또는 여러 밤에 나눠 이어서 검사하는 커서 방식 도입.

테스트:
- 암호화 저장소에서 블롭 본문 1바이트 변조 → Tier 3 가 손상으로 보고 (현재는 통과할 것으로 예상되는 red 테스트부터).
- 키 부재 시 "검증 불가" 분류.

### Phase 4 — 정기 전체 복원 리허설 (F5) [P1]

1. Tier 4 신설: 월 1회(또는 설정), 최신 스냅샷 1개를 임시 경로에 **전체 복원** 후 매니페스트 해시와 전수 대조.
   - 복원 전 대상 볼륨 여유 공간 검사. 부족하면 실행하지 않고 `warning` (조용히 생략 금지).
   - 복원 대상 경로는 원본 데이터와 다른 볼륨 우선. 완료 후 임시 복원본 삭제(삭제는 복원 리허설 전용 폴더 안으로 한정, 경로 검증 필수).
   - 실행 창: 백업 실행 중이 아닐 때. 미니PC 09:00 백업과 겹치지 않게.
2. 대용량일 경우 "스냅샷 전체" 대신 "무작위 디렉터리 서브트리 전체" 모드 제공(설정).

테스트:
- 리허설 중 블롭 하나가 손상된 저장소 → 실패 보고 및 `critical` 알림.
- 여유 공간 부족 → 실행 안 함 + `warning`.
- 리허설 정리 단계가 리허설 폴더 밖을 절대 지우지 않음.

### Phase 5 — 구버전 호환성 회귀 (F6) [P1]

1. `tests/fixtures/repos/` 에 소형 고정 저장소를 버전별로 보관 (Python 엔진, Rust 엔진, 암호화, pack 형식 각 1개 이상). 생성 스크립트도 함께 커밋.
2. 현재 코드로 각 fixture 를 전체 복원해 기대 해시와 대조하는 테스트를 CI(`.github/workflows/ci.yml`)에 추가.
3. 릴리즈 절차에 "새 버전으로 만든 fixture 추가"를 체크리스트로 넣는다.

### Phase 6 — 가시성 (F7) [P2]

1. 웹 대시보드에 계층별 상태 카드: 마지막 성공 시각, 마지막 결과, 연속 실패 수, 다음 예정 시각.
2. 기존 `web/api_snapshots.py` 또는 신규 엔드포인트. API 계약 테스트(`tests/test_api_contract.py`) 갱신.

## 3. 인수 기준 (전체)

- [ ] F1~F7 각각에 대해 "현황 검증" 결과가 보고되었다.

- [ ] `pytest`, `cargo test` 전체 통과.

## 4. 사용자 결정 필요 (작업 시작 전 질문)
