# Track 2-1: 현행 File CAS 대형 파일 Baseline 벤치마크 설계서

## 1. 개요 및 목적
본 문서는 백업시스템의 **Track 2 (FastCDC / Block-level Chunking 검토)** 단계에 진입하기 전, **현행 File CAS (Whole-file Content-Addressable Storage) 체제**에서 대형 단일 파일의 부분 수정이 발생했을 때의 실제 리소스 소비량(I/O, CPU, 메모리, 수행 시간)을 객관적으로 측정하고 기준선(Baseline)을 확립하기 위한 벤치마크 명세서이다.

> **원칙**:
> - 어떠한 최적화나 Fixed Block / FastCDC 구현도 사전에 적용하지 않는다.
> - 현행 제품 코드(`core.snapshot.SnapshotEngine`, `core.storage.BlobStorage`)를 그대로 호출하여 블랙박스/그레이박스 실측을 수행한다.
> - Windows 환경 특성 상 OS 레벨에서 직접 측정이 불가능하거나 왜곡되는 지표는 추정하지 않고 명확한 한계를 기록한다.

## 2. 현행 File CAS 아키텍처 실태 분석

### 2.1 파일 변경 감지 및 백업 파이프라인 구조
1. **1차 Pass (메타데이터 고속 비교 - `SnapshotEngine._execute_backup_pipeline`)**:
   - 파일의 경로, 크기(`size`), 최종 수정 시간(`mtime`)을 직전 스냅샷(`prev_entries_map`)과 비교한다.
   - `size`가 같고 `mtime`이 1초 이내 오차로 동일하며 저장소에 `blob_id`가 존재하면 `unmodified`로 분류하여 파일 바이트를 전혀 읽지 않는다.
2. **2차 Pass (수정/신규 파일 처리 - `BlobStorage.put_file_blob_onepass`)**:
   - 1MB가 변경되어 `mtime`이 갱신되었거나 `size`가 변경된 경우, `modified` 대상으로 분류된다.
   - **Whole-file Stream 해싱 & 압축**:
     - 대상 파일 전체를 4MB 청크(`DEFAULT_CHUNK_SIZE`) 단위로 스트리밍 읽기(`open(..., 'rb')`)를 수행한다.
     - 동시에 SHA-256 해시를 업데이트하면서 Zstandard(Level 1) 또는 zlib로 압축하여 임시 파일(`_temp/tmp_*.blob`)에 쓴다.
     - 읽기가 완료되면 최종 SHA-256 해시를 계산하고, 원자적 파일 이동(`os.replace`)을 통해 `blobs/xx/{sha256}.blob`으로 저장한다.

### 2.2 10GB 단일 파일 + 1MB 변경 시 이론적 발생 부하
- **읽기(I/O Read)**: 단 1MB만 변경되었더라도 파일 단위 해싱 및 압축 구조이므로 **10GB 전체 바이트(10,737,418,240 B)를 반드시 전부 순차 읽기**함.
- **쓰기(I/O Write)**:
  - Base 백업(최초): 10GB 원본을 압축하여 신규 블롭으로 저장소 디스크에 씀 (약 10GB 또는 데이터 엔트로피에 따른 압축 크기).
  - Incr 백업(1MB 변경 후): 1MB 변경으로 인해 파일 전체의 SHA-256 해시가 완전히 달라지므로, **새로운 10GB 블롭이 임시 디스크에 압축 쓰기된 후 최종 블롭으로 승격**됨.
  - 결과적으로 **저장소 용량이 1MB가 아닌 10GB(압축분)만큼 추가 중복 소비**됨.

## 4. 격리 벤치마크 시나리오 설계

### 4.1 첫 검증 (Baseline 1단계)
- **테스트 환경**: 시스템 임시 공간 내 전용 격리 폴더 (`tempfile.mkdtemp` 또는 로컬 전용 벤치마크 경로).
- **데이터셋**:
  - `data_10g.bin`: 10GB 단일 파일 (0바이트 희소 파일이 아닌 난수/엔트로피 패턴 파일 생성으로 압축 회피 및 실질적 I/O 검증).
- **실행 단계**:
  1. **Step 1 (최초 전체 백업 - Base)**:
     - 10GB 파일 생성 직후 `SnapshotEngine.create_snapshot` 호출.
     - 소요 시간, 프로세스 I/O Read/Write, CPU Time, Peak RSS, 저장된 블롭 크기 기록.
  2. **Step 2 (1MB 중간 위치 변경 - Mutation)**:
     - 10GB 파일의 정중앙 오프셋(5GB 지점)의 1MB를 새 무작위 바이트로 덮어쓰기 (`r+b`).
     - 파일 최종 수정 시간(`mtime`) 갱신.
  3. **Step 3 (증분 백업 - Incr)**:
     - 동일 저장소에 대고 `SnapshotEngine.create_snapshot` 2차 호출.
     - 1MB 변경에 대해 시스템이 **얼마나 많은 바이트를 다시 읽고, 얼마나 많은 블롭을 새로 썼는지** 정밀 측정.

### 4.2 후속 확장 계획 (Baseline 2단계 - Track 2-2 예정)
- 변경 크기 변동: `1MB`, `10MB`, `100MB`
- 변경 위치 변동:
  - Head (파일 시작부 0MB 지점)
  - Middle (파일 중앙 5GB 지점)
  - Tail (파일 끝부분 10GB 직전)

## 5. 벤치마크 결과 해석 기준 (Decision Criteria)

1. **증분 백업 Read Bytes ≈ 10 GB**:
   - 현행 시스템이 부분 변경 감지 없이 전체 파일을 재스트리밍/재해싱함을 증명.
2. **증분 백업 Write Bytes ≈ 10 GB (또는 압축 크기)**:
   - 1MB 변경 때문에 10GB의 블롭이 통째로 복제 저장됨을 증명 (File-level 중복제거의 한계).
3. **블록 청킹(FastCDC / Fixed Block)의 필요성 입증**:
   - 위 1, 2번 수치가 명확히 기록될 때 비로소 "Track 2 청킹 도입으로 절감 가능한 I/O 및 저장소 상한선"이 정량화됨.

### 7.2 매트릭스 실측 기반 4대 결정적 분석

1. **변이 위치 무관성 (Location Invariance)**:
   - 변경 위치가 파일의 맨 앞(`Head`, 0B), 중간(`Middle`, 5GB), 맨 끝(`Tail`, 10GB 직전) 어디이든 **I/O Read, CPU Time, 수행 시간은 오차 범위 내(16~18초)로 완벽히 동일**함.
   - 이유: 현행 백업 엔진이 전체 스트리밍 해싱 구조이므로, 변경 위치와 무관하게 0번 오프셋부터 파일 끝까지 무조건 전수 순차 스캔하기 때문임.
2. **읽기 I/O 고정 부하 (Flat I/O Read Penalty)**:
   - 변경량이 1MB이든, 10MB이든, 100MB이든 **I/O Read는 항상 10GB 전체 바이트(10,737,418,240 B + 메타데이터)를 다시 읽음**.
   - 1MB 변경 시 읽기 증폭비: **10,240배** / 10MB 변경 시: **1,024배** / 100MB 변경 시: **102.4배**.
3. **쓰기 I/O 및 저장소의 정직한 증가 (Linear Write Burden)**:
   - 임시 파일 압축 쓰기 및 최종 Blob 이동 구조 상, 변경량이 커질수록(난수 변이 블록이 증가할수록) 압축 블롭 크기가 정직하게 증가함 (1MB 변경 시 약 1~2MB ➡️ 10MB 변경 시 약 11MB ➡️ 100MB 변경 시 약 101MB).
4. **메모리(Peak RSS)의 견고한 안정성**:
   - 10GB 대용량 파일의 전수 순차 스트리밍 처리에도 불구하고 9개 조건 모두 **Peak RSS 45.2 ~ 45.6 MB로 극히 일정**함.
   - 스트리밍 버퍼링(4MB 청크) 구조는 메모리 안정성 면에서는 결함이 없음.

### 7.3 청킹 아키텍처(Fixed Block vs FastCDC) 설계 시사점
- **현행 File CAS의 명확한 한계**:
  대형 파일의 부분 수정 시 '전체 읽기 I/O'와 '전체 SHA-256 CPU 연산'을 피할 수 없음.
- **향후 Track 2 과제**:
  - 만약 **Fixed Block(고정 크기 청킹)**을 도입하면 고정 오프셋(Head/Middle/Tail 덮어쓰기) 변경에 대해서는 해당 블록만 읽고 쓸 수 있어 극적인 개선(1MB 수정 시 1MB 블록만 I/O)이 가능함.
  - 하지만 파일 중간에 바이트가 '삽입/삭제(Shift)'되는 시나리오에서는 Fixed Block은 경계가 밀려 전체 블록이 무효화되므로 **FastCDC(내용 정의 청킹, Content-Defined Chunking)**가 필수적임.
  - 본 9개 매트릭스 실측치는 향후 Track 2에서 구현될 프로토타입의 성능 향상률(Speedup & I/O Reduction)을 입증하는 **절대 기준선(Ground Truth)**으로 기능함.
