# BackupSystem 공식 아키텍처 백서 및 4대 실측 벤치마크 프로토콜

## 1. 개요 및 제품 정체성 (Identity)

BackupSystem은 **Windows 업무 환경에 특화된 3계층(3-Tier) 불변(Immutable) 하이브리드 백업 매니저**입니다.  
글로벌 범용 클라우드 백업 도구와의 기능 경쟁이 아닌, **"Windows 로컬/사내망 환경에서의 작업 일관성, 즉각적인 복구 지연 절감, 그리고 랜섬웨어 변조 방지"**라는 명확한 목표에 최적화된 아키텍처를 가집니다.

---

## 2. 3계층(3-Tier) 복구 아키텍처 공식 정의

CAS(콘텐츠 주소화 스토리지)와 BMR(베어메탈 복구)을 무리하게 하나의 엔진으로 묶지 않고, 장애 유형에 따라 역할을 엄격히 분리합니다.

```text
                        [ BackupSystem ]
                               │
        ┌──────────────────────┼──────────────────────┐
        ↓                      ↓                      ↓
   [ Tier 1 ]             [ Tier 2 ]             [ Tier 3 ]
   CAS Engine           Windows Native         Standalone DR
  (Snapshot/Restore)    (wbadmin / WinRE)   (disaster_recovery.py)
        │                      │                      │
 • 매일 1분 증분 백업   • 주간/월간 시스템 이미지• 무설치 단일 파일
 • VSS 무중단 일관성   • OS Critical Volumes   • 저장소 Bit-Rot 전수 감사
 • WORM 불변성 보존     • 빈 SSD 교체 물리 복원 • 비상 데이터 긴급 구출
 • 11ms 초고속 메타데이터 • WinRE 무인 복구 파이프라인
```

| 계층 | 전담 모듈 | 주요 역할 및 복구 시나리오 | 복구 목표 시간 (RTO) |
|---|---|---|:---:|
| **Tier 1 (CAS)** | `core/snapshot.py`<br>`core/restore.py` | 일상 업무 중 파일 실수 삭제, 이전 버전 롤백, 랜섬웨어 감염 시 시점 복구 | **초(Seconds) 단위** |
| **Tier 2 (BMR)** | `core/system_image.py`<br>`Windows WinRE` | C: SSD 물리적 파손, 메인보드 교체, 부팅 불가(BSOD) 시 새 SSD에 전체 복구 | **수십 분 단위** |
| **Tier 3 (DR)** | `disaster_recovery.py` | 백업 관리 서버 프로세스 자체가 파괴된 극단적 재해 시 독립적 무결성 감사 및 복원 | **비상 즉시** |

## 3. 객관적 기술 정의 및 설계 트레이드오프

### ① VSS (Volume Shadow Copy Service)
- **정확한 정의**: "BackupSystem은 Windows VSS를 백업 엔진의 핵심 경로에 네이티브 통합하여, Windows 업무 PC의 열린 파일, 실행 중인 데이터베이스, 레지스트리의 트랜잭션 일관성 문제를 제품 설계의 중심에서 다룬다."
- 타 솔루션과의 소모적 비교 대신, **Windows 엔터프라이즈 환경에서의 작업 방해 제로(Zero-Lock)**를 가치로 정의합니다.

### ② WORM (Write Once Read Many)
- **정확한 정의**: "기존 백업 객체의 덮어쓰기·변조를 방지하는 소프트웨어 레벨의 Immutable 보호를 제공한다."
- **보안 권고**: 진정한 랜섬웨어 격리를 위해서는 백업 저장소의 Windows 계정 권한 분리 및 오프라인/오프사이트(Durable Queue, NAS, 격리 스토리지)와의 결합이 병행되어야 함을 명시합니다.

### ③ Whole-File CAS vs CDC (Content-Defined Chunking)
- **현재 구조의 명확한 한계 인정**:
  - 현재는 **Whole-File CAS(파일 단위 SHA-256)** 구조입니다.
  - 일반 문서, 소스코드, 사진 등에서는 구조가 단순하고 복원 오버헤드가 극히 적어 최적입니다.
  - 그러나 **수 GB~수십 GB급 대용량 단일 파일(VHDX, Outlook PST, 대용량 DB) 내부의 소량(1MB) 수정 시 파일 전체가 재저장되는 비효율**이 존재합니다.
- **향후 로드맵 (v3.x 선택적 Large-File Chunking)**:
  - 엔진 전체를 무리하게 CDC로 전환하여 청크 인덱스 및 GC 복잡도를 높이지 않습니다.
  - **작은 파일 → Whole-File CAS 유지 (단순성/신뢰성 확보)**
  - **수백 MB 이상 대용량 파일 → FastCDC 기반 선택적 청킹 적용**

## 4. 실측 기반 4대 벤치마크 프로토콜 (The 4 Benchmarks)

수사적 주장이 아닌 정량적 데이터로 제품의 가치와 한계를 증명합니다.

```text
┌────────────────────────────────────────────────────────────────────────┐
│                   BackupSystem 4대 정량 실측 프로토콜                   │
├───────────────────┬────────────────────────────────────────────────────┤
│ 1. 스냅샷 레이턴시│ • 10만 ~ 20만 개 파일 대상 탐색, 증분 백업, 메타데이터│
│    (Benchmark 1)  │   조회 지연 계측                                      │
│                   │ • [실측 달성] 22만 개 파일 환경: Warm Cache 11.46 ms   │
├───────────────────┼────────────────────────────────────────────────────┤
│ 2. 대용량 파일    │ • 10GB 가상 디스크(VHDX) 내 1MB 수정 시 저장소 증가량│
│    오버헤드       │   및 I/O 시간 실측                                    │
│    (Benchmark 2)  │ • [목적] v3.x Large-File CDC 도입의 정량적 근거 마련  │
├───────────────────┼────────────────────────────────────────────────────┤
│ 3. WORM 불변성    │ • 백업 완료된 블롭/스냅샷 JSON 대상 강제 수정, 덮어쓰기,│
│    변조 방어 실측 │   삭제 시뮬레이션 공격 수행                           │
│    (Benchmark 3)  │ • [목적] 저장소 계층의 변조 시도 원천 차단 및 무결성 검증│
├───────────────────┼────────────────────────────────────────────────────┤
│ 4. BMR 물리 E2E   │ • 정상 백업 → 실제 원본 SSD 분리 → 빈 새 SSD 장착   │
│    실물 복구      │   → WinRE 부팅 → wbadmin 복구 → 정상 부팅 성공 확인    │
│    (Benchmark 4)  │ • [목적] 이론이 아닌 물리적 하드웨어 재해 복구 100% 입증│
└───────────────────┴────────────────────────────────────────────────────┘
```
